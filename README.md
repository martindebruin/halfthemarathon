# Half the Marathon I Used to Be

Personal running analytics app — GPS runs recorded on Android, synced and displayed on a self-hosted web app.

## What it does

- Run grid with photos, maps, and splits for every activity
- Year summary pages and lifetime stats
- Route clustering with personal bests per route and top-5 leaderboard on each run page
- Automatic route matching on ingest — new runs are matched to known routes via polyline Hausdorff similarity
- Calendar heatmap and pace trend charts
- Android app for GPS recording with background sync, photo attachment, and auto-generated Swedish run titles
- Calories for app runs filled in from Health Connect via a separate health-sync database
- Whole site behind a single-password login; bearer-token JSON API under `/api/v1`

## Architecture

| Service | Purpose | Port |
|---|---|---|
| `frontend/` | SvelteKit SSR web app | 3000 |
| `webhook-listener/` | Express server handling app run uploads | 3001 |
| Directus 11 | Headless CMS / data store (SQLite) | 8055 |

All services run via Docker Compose behind a reverse proxy. Directus uses SQLite.

## Stack

- **Frontend:** SvelteKit 2 + Svelte 5 (runes), TypeScript, Leaflet, Chart.js, `@directus/sdk`
- **Backend:** Express 4 + TypeScript, Directus 11
- **Infra:** Docker Compose, Nginx Proxy Manager
- **Android:** Kotlin, Room, WorkManager, OkHttp, Coil

## Deployment

Manual rsync + Docker Compose rebuild. No CI/CD.

```bash
# Example: deploy frontend
rsync -avz frontend/src/ <host>:/path/to/halfthemarathon/frontend/src/
ssh <host> "cd /path/to/halfthemarathon && docker compose up --build -d frontend"
```

`VITE_DIRECTUS_PUBLIC_URL` is baked into the frontend bundle at build time via Docker build arg.

### Photo access

The website serves photos through `/photo/{file_id}`, which checks the login session (or the API bearer token) and fetches the image from Directus with the server's token. Transform params `width`, `height`, `fit` and `quality` are passed through.

The Android app still loads photos directly from `{DIRECTUS_PUBLIC_URL}/assets/{file_id}` with no token, so the Directus **Public** policy must keep `read` on `directus_files` until the app uses the proxy. If that permission goes missing (fresh instance, restored backup), every photo in the app returns 403.

## Login

Every page requires a login: one password (`SITE_PASSWORD`), HMAC-signed session cookie valid for 30 days. Changing the password logs out every browser. Being logged in also allows renaming routes on the stats page.

The check lives in each `+page.server.ts` (via `requireLogin()` in `$lib/server/auth.ts`), not only in the root layout: a client-side `__data.json` request can skip an unchanged layout load. `hooks.server.ts` is not used.

## API

JSON API on the site's own domain. Every request needs `Authorization: Bearer <API_TOKEN>`.

| Method | Path | Notes |
|---|---|---|
| `GET` | `/api/v1/runs` | Newest first. Query: `year`, `limit` (1-500, default 50), `offset`. Returns `{ data, meta: { total, limit, offset } }` |
| `GET` | `/api/v1/runs/:id` | Full run, including `splits`, `summary_polyline` and photo URLs |
| `PATCH` | `/api/v1/runs/:id` | JSON body; only `name`, `route_name`, `calories`, `notes` are editable |
| `DELETE` | `/api/v1/runs/:id` | Deletes the run with its photo records and files |
| `GET` | `/api/v1/stats` | Totals, per-year totals, streaks, personal bests |

```bash
curl -H "Authorization: Bearer $API_TOKEN" "https://<site>/api/v1/runs?year=2026&limit=5"
curl -X PATCH -H "Authorization: Bearer $API_TOKEN" -H "Content-Type: application/json" \
  -d '{"calories": 812}' https://<site>/api/v1/runs/843
```

New runs are still created by the Android app through the webhook listener (`POST /api/run`), not through this API.

## Run titles

Each uploaded run gets a Swedish title built from the nearest mass day in the old church year, generated by a local LLM. Runs a few days apart share a mass day, so the newest titles in use are named in the prompt and a repeated title is retried at a higher temperature; the last resort is the holiday name plus time of day. `migrator`'s `backfill-headlines -- --dedupe --apply` separates any collisions already stored.

## Calories from Health Connect

The phone's Health Connect exports to Google Drive daily, and a separate health-sync service imports it into SQLite. The webhook listener mounts that database read-only (`HEALTH_DB_PATH`) and once an hour fills `calories` on app runs from the last 45 days that have none, matching a `running` workout that started within two minutes of the run. Values that are already set are never overwritten. Figures are total energy (active + resting).

The database is read with `sql.js` (WASM): the prebuilt `better-sqlite3` binary segfaulted on `node:20-alpine`.

## Android app

Source at `android/`. Features: GPS recording, pause/resume, background sync to `webhook-run.<domain>/api/run`, photo upload, auto-generated Swedish run titles via reverse geocoding + local LLM.

## Environment variables

See `.env.example` for all required variables. Key ones:

| Variable | Purpose |
|---|---|
| `DIRECTUS_TOKEN` | Static API token used by all services |
| `APP_BEARER_TOKEN` | Auth token for Android app |
| `SITE_PASSWORD` | Website login password |
| `API_TOKEN` | Bearer token for `/api/v1` |
| `HEALTH_DB_PATH` | Read-only path to the health-sync SQLite file (webhook listener); unset disables the calorie fill |
| `TELEGRAM_BOT_TOKEN/CHAT_ID` | Error alerts |
